## 1. O6 的“80/85 被挡”口径冲突（第二节第 2 条）
**结论：O6 写的 85 任务 bank 不是 P6 训练实际使用的任务集合。两者不是同一口径，所以不存在“94% vs 28%”的矛盾。**

- `routea_f8_diag_run03/bank.json` 是 **F8 诊断 bank**：85 个固定 `(world, start, goal)` ticket，425 个条件（每 ticket 5 次）。它是为了 F8 D1 诊断而构造的，被挡 ticket 占 80/85；这个比例只描述该诊断 bank，不描述 P6 的训练分布。
- P6 训练使用 `admission_manifest.json` 的 **53 个 admitted 训练世界**（8 anticipatory / 33 dense_recovery / 8 support_expansion / 4 yaw_lateral_recovery），由 `build_episode_tasks()` 构造 53 个 `EpisodeTaskSpec`；每个回合由环境按角色重新抽 start/goal，**不是** 85 个固定 ticket。代码证据：`entrypoints/pipeline.py:325-350`、`environments/factory.py:build_episode_tasks()`。
- O1 的 1036/3763（27.5%）是按 P18/P19 的**训练回合**统计的：每个回合 reset 时用同一定义（起点—目标直线 0.05 m 采样，最小几何净空 <0.3 m）判被挡。这个数才是 P6 类似训练分布下的回合比例。
- 两个“被挡”定义相同（<0.3 m 直线净空），差异只来自任务集合：
  - O6 的 85-ticket 诊断 bank 故意覆盖了较多被挡 ticket；
  - P6 训练按 53 个世界、角色平衡、随机 start/goal，实际被挡回合约 27.5%。

**O6 回执应改为：**“F8 诊断 bank 中 80/85 ticket 被挡；P6 训练实际为 53 个 admitted 世界，O1 统计的被挡训练回合为 1036/3763（27.5%）。” 原句“P6 训练 bank 80/85”不准确。

## 2. C0 能否直接复用 P18/P19（第二节第 3 条）
**结论：不能把 P18/P19 直接当作 C0；它们不是“P6 配置不变”的匹配对照。**

| 项 | P6 | P18/P19 |
|---|---|---|
| 父权重 | — | P6@u256 |
| 奖励 | v2 | v2 |
| 更新预算 | 256 | 320（从 256 起 64 轮） |
| actor LR | 2e-5 → 1e-5 | **固定 1e-5** |
| 种子 | 202609203 | P18 202611081 / P19 202611082 |
| 源码 | main `d54879fb` | **F7 overlay**（含 `f7` 段，`approach_weight=2.0`） |
| keep 系数 | 0.01061006086489362 | 同 |
| 训练 bank / manifest | admission_manifest 53 世界 | 同 |
| rollout / commits | 1024 / 20 | 同 |

- P18/P19 的 `f7.approach_weight=2.0` 在 reward v2 下不一定生效，但源码闭包和配置字段与 C0 不同；至少 LR 已经从 2e-5→1e-5 改成固定 1e-5。
- 因此：**如果 C0 定义为“P6 配置完全不变”，P18/P19 不能复用，需新跑 2 个 seed；如果用户接受“固定 1e-5 的 F7 code + reward v2”作为 C0 定义，则可复用，但必须在校正后的 C0 定义里写明，不能称“配置完全一致”。**
- P18/P19 各 64 轮、约 16 h/臂；复用可省约 32 h，但要先做上述口径裁定。

## 3. 两条训练能否并行
- 本机：单卡 RTX 4060 Laptop **8 GB**，WSL 内存 **约 7.7 GB**；P6/F9 训练此前均为单进程串行。
- 没有记录到训练进程的峰值显存/内存，因此不能给出“可并行”的实测保证。按现配置（1024 transitions、20 commits、batch 2560 pairs）**不建议直接并行**：两个训练进程很可能触顶 8 GB 显存或 7.7 GB 内存，且会互相拖慢。
- 若要并行，必须先做一次双进程短程实测（记录峰值显存/内存与单轮时间）；在未实测前，第二阶段预算应按**串行 16 h/臂**计。

## 4. O2 的“侧绕”与“末端侧向标准差”口径
### 4.1 侧绕
- 原始 `summary.json` 里的 `safe_and_clear6` **不是侧绕**，它的定义是：`collision == False` 且 `end_free >= 6.0`；只约束末端前方自由距离，不约束横向偏移。Claude 把它读成“侧绕”是不准确的。
- 本包新增 `o2/o2_sideway_summary.json`，明确采用以下可复算口径：
  **sideway = 无碰撞 且 末端前方自由距离 ≥6 m 且 |末端带符号侧向偏移| ≥0.5 m**；左/右按符号分。
- 结果（逐候选比例）：
  - G-orig：no-collision+clear6 **24.7%**，sideway **13.6%**（左 237 / 右 633）。
  - G-rot30：no-collision+clear6 **45.0%**，sideway **40.9%**（左 1163 / 右 1455）。
  - G-rot60：no-collision+clear6 **51.7%**，sideway **48.6%**（左 1081 / 右 2028）。
  - 注：左右计数是候选数，不是状态数；每个状态 32 个候选。
- 这个 0.5 m 阈值是执行侧为“侧绕”补的可复算代理，不是原始指引写死的阈值；若 Claude 要用别的阈值，`o2_candidates.csv` 有 `end_lateral` 可重算。

### 4.2 末端侧向标准差
- `summary.json` 的 `end_lateral_std` 是**跨状态合并**（200 状态 ×32 候选一起算）的总体标准差；它主要反映“不同状态的目标方位/几何不同”，不是同状态散布。
- 本包新增的 `o2_sideway_summary.json` 同时给出**状态内**标准差：先对每个 `state_rank` 的 32 个候选算 std，再取 200 个状态的中位/p90：
  - G-orig：状态内中位 **0.0847 m**（p90 0.1023），合并 **0.5819 m**。
  - G-σ0.2：状态内中位 **0.1677 m**（p90 0.1920），合并 0.6042 m。
  - G-σ0.3：状态内中位 **0.2440 m**（p90 0.2895），合并 0.6316 m。
- 因此“σ0.2/0.3 的散布只增加 4%—9%”是**合并口径**的假象；按状态内，σ0.2 是原样的 1.98 倍，σ0.3 是 2.88 倍。但两者状态内中位仍 **<0.3 m**；σ0.3 的锯齿度中位 0.119，是原样 0.0416 的 2.86 倍，超过“≤2 倍”上限。判据应以状态内为准。

## 5. O5 的两种口径
- 逐状态变化量（先对每个 state 算 |scenario - orig|，再取中位）：去障碍 **0.153 m**、目标侧移 2 m **0.328 m**，比值 **0.465**。这是预先写定的“变化量”口径，**不支持目标捷径**。
- 原始末端侧向位置中位之比：去障碍 0.0998 / 目标侧移 0.3509 = **0.284**；它不是变化量，只作描述，不能替代判据。
- 两个口径都已保留在 `o5_counterfactual.csv`；复算时请按“逐状态变化量”判据。

## 6. 探针 2 的容差
